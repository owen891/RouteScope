<objective>
Harden the existing brownfield production configuration and single-admin authentication path so runtime Settings operations cannot weaken environment-owned deployment controls or disclose effective secrets, and so operators can prove the deployed anonymous boundary before release.

Purpose: A production image is not safe merely because auth code exists; environment precedence, secret persistence, public-route exceptions, and deployed response codes must remain correct through the real Settings and Compose workflows.

Output: Tested config/runtime policies, a redacted write-only Settings contract, operator-controlled credential helpers, authentication boundary tests, and deterministic production probes. Preserve the current dirty implementations as the starting point and do not create a walking skeleton.
</objective>

<threat_model>
## Security Level

OWASP ASVS L1. All High-severity threats are blocking and must be mitigated before this plan completes.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Process environment/YAML to config/runtime | Compose-owned values and file-owned Settings values are combined before constructing live services. |
| Authenticated browser to Settings API | An authenticated operator submits untrusted configuration input and receives a response that must not contain durable secrets. |
| Anonymous network client to Gin API | Public health/version/login traffic and protected management traffic share one HTTP router and dynamic auth middleware. |
| Application to mounted data filesystem | Configuration is persisted beneath the Compose data mount and must not become world-readable. |
| Operator shell to credential/probe helpers | Helpers intentionally handle newly generated credentials or inspect an unauthenticated deployment boundary. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-01 | Tampering / Elevation of Privilege | `config.Load*`, `Manager.ApplyFromFile` | high | mitigate | Task 1 tests conflicting YAML/environment state and requires environment-aware reload before any live collaborator is replaced. |
| T-01-02 | Information Disclosure | startup config creation, Settings GET/PUT, `config.Save` | high | mitigate | Tasks 1-2 keep environment secrets out of YAML, return redacted DTOs, accept only write-only replacements, and force restrictive file permissions. |
| T-01-03 | Spoofing / Elevation of Privilege | `auth.Service`, dynamic auth middleware | high | mitigate | Task 2 tests wrong credentials, token integrity/expiry/subject, exact public routes, anonymous 401, and authenticated protected access. |
| T-01-04 | Tampering | production check scripts | high | mitigate | Task 3 executes both native probes against local HTTP success, unhealthy, redirect, anonymous 200/403/5xx, and connection-refusal cases, requiring nonzero exit on every unsafe state. |
| T-01-05 | Information Disclosure | credential generation scripts | medium | mitigate | Task 3 executes both helpers in temporary roots, byte-checks sentinel `.env`, validates non-placeholder stdout values, and asserts no secret echo from probes. |
| T-01-06 | Repudiation | stateless token logout/revocation | low | accept | Single-operator v1 keeps stateless tokens for upstream compatibility; rotation of the operator-held signing secret plus container restart invalidates outstanding tokens, and TTL remains configurable. |
| T-01-07 | Information Disclosure | browser token in localStorage | medium | accept | This is outside the primary Settings/config boundary and changing to cookies requires CSRF/browser work not present in this phase; v1 retains header-based API use, avoids returning durable Settings secrets, and requires HTTPS at the deployment boundary. |
| T-01-08 | Denial of Service / Spoofing | login endpoint without lockout | low | accept | The single-operator model uses a cryptographically generated high-entropy password; online guessing is infeasible at that entropy, while lockout could deny the sole operator. Network-layer rate limiting remains an explicit deployment defense. |
| T-01-09 | Information Disclosure | legacy query/cookie token extraction | low | accept | Existing compatibility paths remain unchanged; the maintained browser client uses Authorization headers, production documentation requires HTTPS, and no new query-token workflow is introduced. |

## V1 Residual-Risk Disposition

Server-side token revocation, HttpOnly-cookie/CSRF migration, login lockout, and removal of legacy token transports are not silently bundled into this compatibility-focused plan. The accepted rows above document their bounded single-operator v1 rationale; any future change requires its own compatibility and browser/API verification scope. Authentication remaining optional for explicit local/internal deployments is not an accepted production risk: Task 3's production probe blocks release whenever anonymous channel access is not 401.
